# 29 | Test evaluation report: detection quality, false positives, latency, limitations

Phase 2 asks for detection quality on the 50-claim validation set, with a high macro F1 across rule categories and low
false positives on valid claims. This report scores the engine on every labelled example set the repository can supply
(nine sets, 600 public claims plus about 140,000 generated and hand-written ones) and says where each label came from.

The tables below are **generated** by `scripts/render_eval_report.py` from `outputs/evaluation/metrics.json` and
`outputs/evaluation/provenance.json`; a test fails if this file and that evidence disagree. The prose is written by hand
and quotes only numbers that appear in a table.

## 1. Summary

- **The engine reproduces the organizers' answer key exactly on all three public splits.** FAIL detection scores
  F1 1.0 with status accuracy 1.0 and no disagreement on `data/development` (400 claims), `data/validation` (150) and
  `data/stress` (50). The 50-claim split in this repository is `data/stress`; the repository's `data/validation` has 150
  claims. Both are reported, and the harness accepts any other claims-plus-key pair.
- **No valid claim was flagged.** Among the claims the key marks as having no FAIL, the engine raised a FAIL on none, in
  every set (section 5). The tables give the exact upper bound on the true rate for each set; with 160 such claims the
  95% upper bound is under 2%.
- **The 50-claim split is thin evidence on its own.** In it, 9 of the 15 rules have no failing example, so their F1 is
  undefined (section 3). The 400-claim development split covers every rule with at least 10 failures.
- **Larger and harder sets agree too.** 107,635 generated claims, 33,945 mutants of the public claims and 123
  hand-derived boundary cases show no disagreement with the labels (section 7). Those labels are weaker evidence than the
  answer key, and the report says why.
- **One real cost.** Claims that arrive as FHIR lose their authorization records, so rule R009 can only abstain. F1
  falls to 0.9745 on that path and most clean claims receive an abstention on R009 (section 4). The abstention goes to a
  human; no failing claim becomes a pass.
- **Latency.** The rule engine's median per claim is under one millisecond on the test laptop (section 8).

A perfect score on public data does not by itself show the system is better than an alternative; sections 6 and 9 say
what would.

## 2. What was measured, and on what

- **Tier A, organizer answer key.** The only external truth. The organizers' synthetic dataset, v1.0.0.

### Definitions

- **Positive class: `FAIL`**, as in the organizers' scorer `src/evaluate.py`. Precision, recall and F1 are computed on
  that class. `UNABLE_TO_ASSESS` is scored separately: an abstention is not an error, but an unnecessary one costs a
  reviewer time.
- **Rule categories.** The rulebook defines none, so these are our grouping by what a rule checks. Counts are pooled
  within a category, then F1 is averaged across the categories where it is defined.

| Category | Rules |
|---|---|
| Completeness and arithmetic | R001, R007, R012 |
| Eligibility and coverage | R003, R004, R005, R015 |
| Timing | R002, R014 |
| Authorization and documentation | R008, R009, R010 |
| Catalogue, pricing and duplicates | R006, R011, R013 |

  Macro F1 is also reported by severity (11 high, 4 medium rules) and over all 15 rules, so the grouping cannot flatter
  the result. A category with no `FAIL` in a set has an undefined F1; it is excluded from the macro and listed, not
  scored as 0.
- **Valid claims.** *Claims with no gold FAIL*: the claim-level false-positive rate is the share of these where the
  engine raised any FAIL. *Fully clean claims* (every result PASS or NOT_APPLICABLE): the same rate, the share where the
  engine abstained on any rule, and the result-level false-alarm rate.
- **Upper bound.** With few or no errors, a point estimate misleads. Each rate is shown with the exact one-sided 95%
  upper bound. By the rule of three, claiming an error rate below 1% needs about 300 error-free examples.

Every disagreement in every set is in the table above. All of them are on the FHIR path (S5) and all of them are
rule R009 becoming `UNABLE_TO_ASSESS`. A FHIR bundle in this dataset carries no authorization records, so R009
(authorization record matches service) cannot be checked. The engine says so instead of guessing: the failing claims
become abstentions that route to a reviewer, and **no failing result became a PASS**. The cost is reviewer workload: the
valid-claims table shows how many fully clean claims receive an unnecessary abstention on this path.

## 9. Limitations

- **A perfect public score cannot rank this system against a better one.** The answer key is deterministic and the
  public claims were available while the rules were built; a correct implementation of the rulebook should reach 1.0 here. What
  the sets can show is the absence of errors found, with the upper bounds above.
- **The oracle shares our reading of the rulebook.** Tier B and C measure agreement and self-consistency. If the team
  misread a rule, both implementations would agree and be wrong, and only the organizers' key (tier A) would show it.
- **Tier C is small and written by us**, and each case labels only the rules it names (140 labelled results in 123
  claims).
- **The rule categories are our grouping.** Another grouping would give different macro numbers; the severity and
  all-rules macros are reported alongside for that reason.
- **Per-rule F1 can rest on very few failures.** In the 50-claim split 9 rules have none and the others as few as 3; in the
  validation split the smallest count is 4. Use S1, the pooled category view and the larger sets for conclusions.
- **The claims are synthetic.** The mix of failures says nothing about the frequency of real claim errors.
- **FHIR loses authorizations by design**, so R009 cannot be assessed on that path; this report quantifies the effect
  rather than removing it.
- **Latency is from one laptop**, in one process, with warm caches; it is not a load test.
- **The explanation step is not part of these metrics.** Detection is deterministic; the quality of AI explanations is
  evaluated in `docs/17` and `docs/21`.
- **Nothing here measures review quality or decisions.** Routing and reviewer feedback are Phase 2 work with their own
  evidence.

## 10. Reproduce

```bash
python scripts/evaluate_phase2.py --out-dir outputs/evaluation   # about 6 minutes; writes metrics.json and provenance.json
python scripts/render_eval_report.py                             # fills the tables in this file
python scripts/render_eval_report.py --check                     # exits 1 if this file is stale
```

Accuracy numbers are deterministic (fixed seeds: 20260927 for S7, 20261004 for S8); latency numbers vary with the
machine. The commit the evidence was produced at is recorded in both JSON files.
